1. ORIGINAL PROJECT AND GOAL
============================
The repository started as a partially complete Cloudflare-based work-update automation application. Its legacy components include a Cloudflare Worker, D1 schema/query files, scheduled/cron routes, Gemini and Teams integrations, and a browser extension. The initial instruction was to inspect before replacing anything, preserve working business logic, and migrate incrementally to AWS without deleting Cloudflare resources.

The desired AWS application is personal, accessible from a phone or desktop through HTTPS, and must keep processing if the user's device is turned off after submitting a session. The user asked for serverless infrastructure and no always-running EC2 instance. The intended cloud services are S3, CloudFront, Cognito, API Gateway, Lambda, DynamoDB, EventBridge Scheduler, Secrets Manager, CloudWatch, Terraform, and GitHub Actions OIDC.

The user later specified the desired business flow:
  - Enter clock-in time, send an immediate Teams clock-in notification, and save session state.
  - Optionally enter clock-out time; schedule report processing/checking based on it.
  - Run a recurring fallback at 00:30 Asia/Kolkata.
  - If no clock-in exists, do nothing.
  - If clock-out remains absent, use a configurable default time (user said "11:30 or something"; AM/PM is not confirmed; 23:30 local was suggested, not approved).
  - If clock-out is before the fallback, verify delivery at 00:30, recover if needed, then archive/clear active session only after successful delivery.
  - If clock-out is after the 00:30 worker (example 00:45), schedule a check at clock-out + 10 minutes (example 00:55), send only if not already delivered, then archive/clear after confirmed delivery.
  - Keep old completed entries in history/logs while current active page becomes null/empty.
  - Only the 00:30 fallback or the post-00:30 clock-out scheduled check may archive/clear session state. Failed and ambiguous delivery state must remain visible.

The final Teams message should follow the owner's provided format:

ELEPHANT

Clock in - {HH:mm}

Clock out - {HH:mm}

Total hours - {H} hrs {MM} mins

Current ticket - {ticket}

Email - {email status}

Blocker - {blocker or none}

Today's update - {Gemini-generated update, usually three concise paragraphs}

The sample from the owner showed 14:12 clock-in and 23:20 clock-out = 9 hrs 08 mins. Its example work details are formatting references only and must never be reused as fabricated facts.

3. AWS ARCHITECTURE AND HOW IT WORKS TODAY
==========================================
Static request flow:
  Browser -> CloudFront HTTPS -> private S3 frontend using Origin Access Control.

Authentication/API flow:
  Browser -> Cognito OAuth authorization-code + PKCE -> ID token in sessionStorage ->
  API Gateway HTTP API JWT authorizer -> session_api Lambda -> DynamoDB.

Scheduled processing flow:
  Session API creates/updates EventBridge Scheduler schedule -> report_processor Lambda.
  A recurring EventBridge Scheduler fallback invokes report_processor every day at 00:30
  in the configured IANA timezone (default Asia/Kolkata). No phone/browser background job
  is required.

Processing:
  Processor re-reads latest session; checks scheduleVersion and delivery state; attempts a
  conditional DynamoDB lease; calculates work duration; retrieves Gemini and Teams values
  from Secrets Manager; calls Gemini; records generated report; sends Teams message; records
  delivery/completion state. AWS Lambda currently runs outside a VPC; public HTTPS egress
  works without a NAT Gateway.

Resources in Terraform:
  - S3 private frontend, CloudFront distribution/OAC/security response headers.
  - Cognito user pool/client and optional hosted UI domain.
  - API Gateway HTTP API/JWT authorizer/access logs.
  - Session API Lambda and report processor Lambda, runtime roles and log groups.
  - DynamoDB on-demand table with status GSI, encryption, point-in-time recovery and TTL.
  - EventBridge Scheduler schedule group, recurring fallback, DLQ, invocation role.
  - Secrets Manager empty secret containers for Gemini and Teams values.
  - CloudWatch alarms and logs.
  - Per-account deployment role and OIDC provider in bootstrap.

No EC2, ECS, EKS, RDS, VPC, or NAT Gateway is included. Do not add one without a concrete requirement.

Important gaps versus the new owner requirements:

  2. Current message to Teams is generated report text alone; it does not wrap it with ELEPHANT,

  4. AWS implementation does NOT retrieve full conversation content from shared ChatGPT URL.
     It stores URL but requires pasted transcript. It must never scrape private cookies or
     fabricate when transcript is missing.
  5. Current missing clock-out fallback is midnight at the end of the work date, not 23:30.
     Owner's "11:30" is ambiguous and needs confirmation before changing default.
  6. Current explicit clock-out schedule is at clock-out, not clock-out + 10 minutes after
     the 00:30 fallback. This new behavior is not implemented.
  7. Completed entries remain in DynamoDB until TTL cleanup; no atomic archive-to-history and
     clear-active workflow exists. Current key is PK=USER#{sub}, SK=SESSION#{workDate}.
  8. Current UI loads by work date; it has no separate active-session-empty/history view.
  9. Current Gemini prompt requests exactly three paragraphs and forbids "today"/"yesterday";

ChatGPT retrieval limit: the legacy Worker has a shared-link HTML preview fetch, but that does

Teams delivery risk: incoming webhook and DynamoDB do not share a transaction or idempotency

delivery cannot be guaranteed. Current processor records DELIVERY_UNKNOWN before external
side effect and blocks blind automatic retry. Preserve explicit reconciliation/duplicate warning.

Deleting/updating a schedule is not enough to cancel an already running Lambda; always validate
latest item and version.

Suggested future active/history design (requires deliberate migration; not current code):
  - PK=USER#{sub}, SK=ACTIVE for current session.
  - PK=USER#{sub}, SK=LOG#{workDate}#{sessionId} for durable history.
  - After confirmed Teams delivery only, transact conditionally on version/status to archive
    finalized non-transcript fields/report and clear ACTIVE atomically.
  - Only fallback at 00:30 or post-00:30 scheduled check may execute archive/clear.
  - Preserve active record for failure or DELIVERY_UNKNOWN. TTL applies only to history after
    a documented retention period; TTL is not a scheduler.


6. TERRAFORM, STATE AND MULTI-ACCOUNT DESIGN
============================================
Bootstrap creates:
  - Account-local GitHub OIDC provider for token.actions.githubusercontent.com, audience
    sts.amazonaws.com (or reuses existing provider by ARN).
  - Project/environment GitHub deployment IAM role and explicit policy.
  - Private, versioned, encrypted Terraform state S3 bucket.
  - Private, versioned, encrypted Lambda artifacts S3 bucket.

Bootstrap state is local by design; keep it backed up securely and never commit it. Main stack
uses S3 state and Terraform native lock object at key:
  <account-id>/<environment>/terraform.tfstate
and `use_lockfile=true` (Terraform >=1.10). Distinct account/environment keys/buckets prevent
state collision. Bootstrap must exist before the main backend initializes.

Deployment/runtime roles are separate. The GitHub deployment role manages defined project
resources and passes only app roles to Lambda/Scheduler where appropriate. Runtime roles are
limited to their data/secrets/schedules/logs. The role was not made account administrator.
Some AWS APIs require `Resource="*"` (e.g. CloudFront global control plane, Logs group listing
and API Gateway log delivery, Cognito domain description); those statements are action-limited.
Separate accounts are recommended for production isolation. SCPs/boundaries/quotas can still
block another account.

Asia/Kolkata. Treat these as current dev settings, not hardcoded architecture constants.

8. TERRAFORM/APPLY/DESTROY ERRORS AND FIXES MADE
===============================================
The many observed failures were mostly specific AWS IAM permissions, not broken state locking.
The bootstrap deployment policy source was expanded with concrete actions, scoped by app prefix,
region, and account where AWS supports resource scoping. Important observed errors and remedies:

  - logs:CreateLogGroup -> scoped creation permissions for app Lambda/HTTP API log groups.
  - cloudfront:CreateResponseHeadersPolicy -> CloudFront response header policy lifecycle.
  - cognito-idp:SetUserPoolMfaConfig/GetUserPoolMfaConfig -> pool MFA read/write.
  - dynamodb:UpdateContinuousBackups/DescribeContinuousBackups -> point-in-time recovery
    enablement/read.
  - scheduler:ListTagsForResource -> schedule/schedule-group tag inspection.
  - iam:ListRolePolicies/ListAttachedRolePolicies -> Terraform role policy refresh.
  - S3 GetBucketAcl/CORS/Website/Accelerate and related reads -> bucket configuration refresh.
  - secretsmanager:GetResourcePolicy -> secret metadata policy read.
  - logs:DescribeLogGroups -> read-only global list (AWS requires wildcard resource scope).
  - API Gateway POST/TagResource -> HTTP API and stage/route/tag operations.
  - logs:CreateLogDelivery and related APIs -> API Gateway access log delivery configuration.
  - cognito-idp:DescribeUserPoolDomain -> user pool domain state read, global resource scope.
  - lambda:GetFunctionCodeSigningConfig -> Lambda refresh inspection.
  - cloudwatch:ListTagsForResource -> alarm tag inspection.
  - S3 NoSuchKey while creating Lambda -> pipeline now builds/uploads/verifies packages before
    Terraform plan/apply. This was artifact ordering, not IAM.
  - S3 BucketNotEmpty during destroy -> versioned frontend needs all versions removed; confirmed
    destroy enables `force_destroy` in a preparatory apply and role has ListBucketVersions and
    DeleteObjectVersion for frontend buckets/objects.
  - iam:ListInstanceProfilesForRole during destroy -> added role inspection permission.
  - Partial destroy retry could recreate already removed protected resources -> preparatory
    destroy step checks `terraform state list` and only targets still-managed resources.

For a new permission failure: identify the exact AWS API action/resource, determine if it is
needed by Terraform refresh, create/update, deploy, or destroy, add only the needed permission
to bootstrap/main.tf, apply the bootstrap policy using authorized bootstrap state, then rerun a
fresh plan. Never attach AdministratorAccess or use broad wildcards merely to silence errors.

Most recent destroy partially removed resources and then failed. Do not assume this code state
means a fresh destroy already succeeded; inspect current remote run and AWS state read-only.
